> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the deploy's checks as one required check, `checks`, on every pull request, commit the
ruleset that lets a change reach `main` only through a squash-merged pull request whose check
passed, and apply that ruleset on GitHub.

**Architecture:** Task 1 renames `deploy.yml` to `ci.yml` (one workflow for both events), adds
`.github/rulesets/main.json` and adds `src/ci.test.ts`, a guard test whose pure checker `problems()`
reads the workflows line by line and fails when they and the ruleset drift apart. The test goes red
on the renamed old workflow and green on the new one, inside one commit. Task 2 documents the gate
in CONTRIBUTING. Task 3 runs the local gates into a git-ignored record. Task 4, the controller's
alone, opens the pull request, applies the ruleset after the merge and probes it on GitHub, each
outward step on the owner's word.

**Tech Stack:** GitHub Actions (`actions/checkout@v7`, `setup-node@v7`, `upload-pages-artifact@v5`,
`configure-pages@v6`, `deploy-pages@v5`); GitHub repository rulesets through `gh api` (REST

## Review Focus

1. **Comment and blank lines in a workflow.** A maintainer annotates the required job
   (`    # Must match .github/rulesets/main.json.` above `name:`), puts a column-0 comment between
   triggers or jobs, comments a key out (`    # if: always()`, `  # pull_request:`), or writes
   `pull_request: # no filters`. Expected: a comment or blank line never ends a block and is never a
   key, so the annotated file gives `[]`, and a commented-out trigger counts as missing. Pinned by
   `skips comment and blank lines at any indent` and `does not read a commented-out trigger`.
2. **A quoted or commented job name.** `name: 'checks'`, `name: "checks"` and
   `name: checks # required by the ruleset` each report `checks` and give `[]`; misreading them
   would fail the guard on a cosmetic edit. Pinned by `reads %s as checks`.
3. **A second workflow that is not a full block-form workflow:** a reusable one
   (`on: workflow_call`), an empty file, or flow-form `jobs:`. Expected: no crash; its `on:` matters
   only when it holds a required job; its jobs still count for rule 2; jobs it cannot read are
   reported, so they cannot hide a second `checks`. Pinned by
   `reads the jobs of a second workflow whose on: is not a block`,
   `still counts a required job in that workflow` and `reports a workflow whose jobs it cannot read`.
4. **A job whose check name the reader cannot know:** `name: ${{ matrix.name }}`, or a `strategy:`
   matrix on the required job (GitHub then reports `checks (22)`, never `checks`, so every pull
   request would wait forever while the guard stayed green). Expected: the expression is reported,
   and neither job counts as reporting `checks`. Pinned by `reports a job name it cannot evaluate`
   and `does not count a matrix job as reporting its plain name`.
5. **CRLF line endings** (a Windows checkout with `core.autocrlf`). Expected: what LF gives: `[]` for
   the good workflow, and a job-level `if:` still found. Pinned by `reads CRLF line endings` and
   `finds a job-level if: in CRLF text`.

The reader (_Testing_), for each workflow text:

- Split lines on `\r?\n`. A blank line, or one whose first non-space character is `#`, is skipped
  everywhere: it never ends a block and is never a key.
- A key line is: spaces, a key of `[A-Za-z0-9_-]+`, `:`, then nothing or a space and a value. Its
  indent is its count of leading spaces. A value loses a trailing comment (a `#` preceded by a space
  or tab, to the end of the line) and its outer spaces.
- The `on:` block is the indent-0 key line `on` with an empty value; its body runs to the next
  indent-0 line. Its triggers are the body's indent-2 key lines. The `pull_request` trigger has a
  value when its value is not empty, and nested keys when a body line between it and the next
  indent-2 line is indented deeper.
- The `jobs:` block is the indent-0 key line `jobs` with an empty value, bounded the same way. Its
  job IDs are the body's indent-2 key lines; a job's own keys are the indent-4 key lines up to the
  next indent-2 line. Deeper lines (steps, a step's `- if:`, `environment:`'s `name:`) are never job
  keys. With no such `jobs` line, or with an indent-2 line in the block that has a value (a
  flow-form job), the workflow gets R1 and contributes no jobs.
- A job reports under its `name:` value, or under its ID when it has no `name:`. A `name:` value in
  matching single or double quotes is the text between them (a `#` inside is text). A job reports
  under no name when its `name:` holds `${{` (R2) or when it has a `strategy:` key.

The ruleset: a `rules` entry counts for rule 1 when it is an object whose `type` is
`'required_status_checks'`; a ruleset that is not an object, or whose `rules` is not an array, has
none. With exactly one such rule, its checks are `parameters.required_status_checks` (not an array:
an empty list); a check's context is its `context` when that is a string, else `''`.

The messages, fixed. `<file>` is the key in `workflows`, `<id>` a job ID, `<context>` a check's
context, `<n>` a count, `<value>` `JSON.stringify` of the `integration_id`:

| --- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| M1a | rule 1: not exactly one `required_status_checks` rule (no check is then read) | `ruleset: expected exactly one required_status_checks rule, found <n>`                 |
| M1b | rule 1: that rule's list of checks is empty                                   | `ruleset: the required_status_checks rule lists no checks`                             |
